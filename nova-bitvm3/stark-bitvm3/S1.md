# S1: finalized-circuit lowering

This stage imports the ten gate families from the pinned upstream `circuits::Circuit` into a Boolean constraint checker. It accepts a witness only when every field word is canonical, all gates hold, and every constant and public output agrees with the caller's trusted policy. The graph itself is trusted code/configuration; a prover-chosen graph or policy is outside the interface's security contract.

## Code and test commands

`lowering/` has no third-party dependencies. Its production dependency is the local S0 core. `upstream/` imports actual native types from `starkware-libs/proving` at `e9a38e12d09979f7a8625e233a80fecac6c38f02`, without enabling the prover feature. `adapter/tests/lowered.rs` runs the lowered all-gate fixture in execute, garble and evaluate modes.

```sh
cargo +1.90.0 test --locked --manifest-path nova-bitvm3/stark-bitvm3/lowering/Cargo.toml --features test-utils -- --nocapture
cargo +1.90.0 test --manifest-path nova-bitvm3/stark-bitvm3/upstream/Cargo.toml --test conformance -- --nocapture
cargo +1.90.0 test --manifest-path nova-bitvm3/stark-bitvm3/adapter/Cargo.toml --test lowered -- --nocapture
```

## Gate coverage

The supported families are Add, Sub, Mul, PointwiseMul, Eq, TripleXor, M31ToU32, BlakeG, Permutation and Output. The importer destructures every field of the upstream Circuit without a wildcard. A changed gate inventory must cause a compile failure during a future upstream update.

It requires `FinalizedContext` and completion of guessed-variable finalization. That finalization inserts the M31 and U16 witness-domain constraints, which are imported along with the arithmetic checks. The importer pins the context's constants, and every output must have an expected value. The zero, one and u slots are fixed even for manually built programs.

Permutation constraints use deterministic bitonic sorting, with exact multiplicities and padding for non-power-of-two lengths. Packed u32 operations constrain both 16-bit limbs and both zero extension limbs. Shape, reference and permutation-work limits are checked before Boolean construction.

## Acceptance contract

For a fixed trusted program P, expected bindings B and raw witness W, the acceptance wire is the conjunction of canonical encodings, gate constraints and bindings. After canonical decoding, successful acceptance implies that the imported upstream native gate relation holds and that B matches. The tests compare this relationship against compiled upstream code. This is not a formal proof of the compiler.

The witness includes values of internal upstream circuit variables. Each is constrained in the Boolean relation; they are not trusted host-computed shortcuts. This changes the garbled input layout and may increase input commitment and memory costs. A full BitVM3 integration must authenticate that layout and bind the exact circuit and application statement before accepting an operator claim.

Upstream's Output gate records an interface obligation. Its native `check` method alone does not fix the public value. A regression checks the collapsed all-zero assignment and ensures the explicit bindings reject it. This demonstrates a required adapter boundary, not a claim that the surrounding upstream proof system omits its own public-output checks.
