# S4: the Stwo circuit verifier through the Boolean lowering

S3q cleared the native-proof blocker for the Shinigami standalone trace. S4 starts the verifier side: how large is the pinned Stwo verifier once it is expressed as a Boolean relation, and does that relation accept a real proof and reject changed ones?

The pins are the S2 pins: `starkware-libs/proving` at `e9a38e12d09979f7a8625e233a80fecac6c38f02`, imported through the S1 lowering (`stwo-bitvm3-lowering`, `stwo-bitvm3-upstream`). The lab is the new crate `s4-cairo/` (nightly-2026-01-15, no Nova, no SP1, no CUDA, no garbling).

## What upstream's verifier stack looks like

A Cairo proof is not verified by the Boolean relation directly. Upstream verifies it inside a circuit (`circuit-cairo-verifier`), proves that circuit with a circuit prover, and the last link is a **1-to-1 circuit verifier** (`circuit_verifier::multiverifier::build_multiverifier_circuit` with one input). That last circuit is small and proof-independent in shape, so it is the natural thing to turn into a Boolean relation. Its public statement is exactly two values: the preprocessed root of the proved circuit and the 8-word output digest. The Cairo verifier circuit exposes the program's Blake2s output digest, and the Cairo proof must carry exactly two 128-bit output cells holding it.

## Template sizes (proof-independent)

Non-free ANDs are the garbling cost (XOR is free). Counts are exact, from `count.rs`: a per-constraint-shape count that matches the monolithic count to the last gate wherever both ran.

| Circuit | Config | Vars | Constraints | Raw input bits | Non-free ANDs | XORs |
|---|---|---:|---:|---:|---:|---:|
| Final 1-to-1 verifier, **production recursion config** (`PRIVACY_RECURSION_CIRCUIT_PREPROCESSED_ROOT`) | blowup 2, 35 queries, pow 26, fold 4, trace log 21 | 2,961,135 | 1,177,730 | 379,025,280 | **4,783,261,848** | 9,214,805,428 |
| Final 1-to-1 verifier, **fixture config** (the config of upstream's committed proof) | blowup 3, 23 queries, pow 27, fold 4, trace log 21 | 2,057,107 | 819,367 | 263,309,696 | **3,338,462,413** | 6,435,641,823 |
| Cairo verifier circuit (privacy bootloader, 2,584-word program, 57 components, zk blinding 45) | blowup 3 | 5,322,183 | 2,488,198 | 681,239,424 | 14,693,909,921 | 30,134,062,230 |

Gate mix of the production final verifier: add 112,760; sub 114,837; mul 128,016; pointwise-mul 43,851; eq 14,546; triple-xor 59,624; m31-to-u32 107,777; Blake-G 596,240; 70 permutations (widest 152, total width 9,310); 9 output gates. The fixture-config verifier has Blake-G 413,840 and 46 permutations. Blake-G gates dominate the ANDs, as expected from Merkle path hashing.

Consequences:

- At the S2 rate of 16 bytes per non-free AND, garbling the production final verifier is about 76.5 GB of ciphertext and the fixture-config one about 53.4 GB. The S2 measurement (141.6 million non-free gates, a 2.11 GiB ciphertext file, 24.7 s to garble) covers a test verifier 24 to 34 times smaller by AND count than these two; its timings and sizes are a lower bound, not a forecast.
- A Cairo program is **not** verified at the Boolean level directly. In the Cairo verifier circuit every program word costs about 142.4 thousand ANDs (measured by replacing the 2,584-word program with N words), so verifying a 169,856-word Shinigami executable as a fixed program would add about 24 billion ANDs on top of the 14.3 billion base, roughly 38.5 billion in total. The privacy bootloader (2,584 words) running the executable as a task, followed by the recursion into the final 1-to-1 verifier, keeps the Boolean statement at the 3.3 to 4.8 billion level for any program. That is the architecture BitVM3 should target, and it means Shinigami must be proved *under the bootloader* rather than as a standalone executable.

## Evidence: a real proof through the Boolean relation

`s4-cairo check` runs upstream's committed proof of the padded privacy Cairo-verifier circuit, `test_data/multiverifier/proof_cairo.bin` (182,900 bytes), through the final 1-to-1 verifier built with the **fixture config**. The proof configuration, the preprocessed root and the output digest come from upstream's fixture constants (`circuit_prover::test_utils`), never from the proof; the proof is deserialized against the pinned proof configuration and every byte must be consumed.

Local run (WSL, 20 threads, one shot, peak RSS 1.48 GB, 36 to 44 s wall):

| Step | Result |
|---|---|
| Native relation (`FinalizedContext::is_circuit_valid`) | accepted (0.1 s) |
| Proof-bearing circuit equals the proof-free template | yes (the template is a faithful topology) |
| Imported program | 2,057,107 variables, 819,367 constraints, 8 public output pins |
| Boolean relation, sharded (410 shards of 2,000 constraints, 16 threads) | **accepted**, 4.4 to 6.9 s |
| Mutations of the proof (re-synthesizing every internal value against the same trusted template) | `trace_at_oods[0]+1`, `claimed_sums[0]+1`, `fri_last_layer_coef+1`, `oods_pow_nonce+1`, `fri_witness_first+1`, `channel_salt+1`: **all six rejected by the native relation and by the Boolean relation** |
| Non-canonical alias (a variable holding p instead of 0) | rejected by the Boolean relation |

CI reproduction: [run 42946737257](https://github.com/patrickdugan/garbled-snark-verifier/actions/runs/42946737257), job `s4-verifier-circuit`, commit `762cd77`, hosted runner (4 threads): the same acceptance, the same six rejected mutations and the alias rejection; Boolean relation 11.6 s, whole check 91.6 s, peak RSS 633 MB; every template count above identical to the local figures; the unit test passes. Artifact `stwo-s4-verifier-circuit-762cd77aedf312fd3681abe50be673446d3fc7b3` (zip digest `sha256:b04e2811fe0daec73e2dbdb9355db99f9f4696d21c953bb7c73e810c75de23b7`).

Sharding: a program of 2.06 million variables is split into sub-programs over the variables each shard touches, each re-pinned. The conjunction of the shards equals the monolithic relation; a unit test (`shard::tests::sharding_never_changes_the_verdict`) checks equal verdicts for shard sizes 1 to 1000 and for every single-limb mutation of the all-gate fixture. The shard-summed ANDs (3,412,801,060) exceed the monolithic count (3,338,462,413) by 2.2% because shared variables are decoded in each shard that reads them; the monolithic count is the one that matters for garbling.

## S4c: a production-config proof through the Boolean relation

The committed `test_data/privacy/recursion_proof.bin` (43,300 bytes) is a recursion proof under `FriParams::test_params()`: deserializing it with the production proof configuration fails (`ValueOutOfRange`) and its root is not `PRIVACY_RECURSION_CIRCUIT_PREPROCESSED_ROOT`, so it cannot serve as production evidence. A production-config proof was therefore generated with upstream's own pipeline. `s4-prove/` builds against the pinned revision (WSL, `-C target-cpu=native`, 5.5 minutes cold) and runs the privacy bootloader on upstream's fixture PIE `privacy_tx_cairo_pie.zip`, proves the Cairo execution (production Cairo profile: blowup 3, 23 queries, pow 27, trace log 20), proves the Cairo-verifier circuit (production circuit profile: blowup 2, 35 queries, pow 26, trace log 21), verifies the result with upstream's `verify_recursive_circuit`, and stores the raw recursion proof and the 32-byte output digest.

| Quantity | Value |
|---|---|
| Prover wall clock, whole pipeline | 17.8 to 18.8 s on 20 cores (Cairo proof 8.7 s, recursion proof 15.5 s) |
| Prover peak RSS (`/usr/bin/time -v`) | 14.3 to 14.6 GB (WSL limit 20 GB) |
| Emitted proof | 226,416 bytes (35-byte header plus zstd); raw recursion proof 263,812 bytes |
| Bootloader output | 9 felts, digest `1f597285…8e9cb4`, root = the production constant |
| Determinism | two runs byte-identical; the generalized `s4-prove` pipeline is byte-identical to `privacy_recursive_prove` |

`s4-cairo check-prod` then runs this proof through the same checks as the fixture proof, against the **production** template (blowup 2, 35 queries; 2,961,135 variables, 1,177,730 constraints, equal to the template counted above):

- native relation accepted (0.1 s);
- Boolean relation, sharded (589 shards, 16 threads): **accepted**, 8.1 s, summed ANDs 4,889,964,208 (2.2% over the monolithic 4,783,261,848 because of re-decoded shared variables);
- the same six mutations and the non-canonical alias: all rejected by the native and by the Boolean relation;
- whole check 54.8 s, peak RSS 1.56 GB.

So the production final 1-to-1 verifier, as a Boolean relation over its full 4.78 billion non-free ANDs, accepts a production proof and rejects changes. This check is local only: the prover needs 14.6 GB, which a hosted runner does not have, so CI covers the fixture config.

## S4d: Shinigami under the privacy bootloader does not fit the pinned profiles

The Scarb executable has a `Bootloader` entrypoint (169,856 bytecode words; builtins output, range_check, bitwise), so it can be handed to the privacy bootloader as a Cairo-1 task. `s4-prove` does so (the upstream function takes only a PIE and keeps its helpers private, so the pipeline body is repeated, verified byte-identical on the PIE). The bootloader executes the task, but the Cairo prover then panics in the twiddle table ("Not enough twiddles!"), because the trace exceeds the fixed 2^20-row profile. The adapter's dimensions show why; the cost is the **program length**, not the execution:

| Run | Steps | Memory cells | Notes |
|---|---:|---:|---|
| Shinigami standalone (S3) | 157,303 | 378,312 max address | the S3q proof |
| Fixture PIE under the privacy bootloader | 275,860 | 328,836 | proves in 18 s |
| Shinigami as a task, program hash Blake | 2,770,649 | 3,008,238 | bootloader executed; prover rejects the size |
| Shinigami as a task, program hash Poseidon | 1,093,754 | 1,815,096 | dimensions only |
| Shinigami as a task, program hash Pedersen | 1,518,384 | 2,018,918 | dimensions only |

With Blake the run costs 17.6 times the standalone steps and 7.9 times the standalone memory; this is consistent with the program being hashed as 32-bit words, eight per felt, about 1.36 million of them. Components hold one row per memory cell and the production small profile caps a component at 2^20 rows, so 1.8 to 3.0 million cells need 2^21 to 2^22 (inference; only the Blake run was proved against the cap, and it failed). The registry's large-proof flow (`privacy_large_proofs`, blowup 1, 70 queries) only has leaf verifiers for trace log sizes 25 to 29, matched exactly, and lifts to the 2^25 preprocessed height, which is far beyond this machine. Neither pinned flow can carry this executable.

Ways forward, none built yet: (1) shrink the program, since the bootloader cost per word is about 6 steps with Poseidon hashing and 16 with Blake (the engine's 169,856 words are the cost, and a CSV and SHA256 only wrapper needs a small fraction of the engine); (2) a custom laboratory profile at Cairo trace log 21 with Poseidon program hashing, which changes the Cairo-verifier circuit and its recursion circuit sizes and probably needs a machine with 30 GB or more; (3) the large-proof flow on rented compute. Each changes the final verifier's configuration, so its Boolean size must be re-measured rather than scaled.

## What this establishes, and what it does not

Established, at the pinned revisions:

1. The Boolean size of the production final verifier (4.78 billion non-free ANDs, 379 million raw input bits, 2.96 million variables) and of the Cairo verifier circuit, as exact, reproducible counts.
2. A Boolean lowering of a circuit-proof verifier **accepts real proofs** (the committed fixture proof at blowup 3 in CI and locally, and a freshly generated **production-config** recursion proof locally) and rejects six independent proof mutations and a non-canonical alias each time.
3. The architectural conclusion above: keep the Cairo program out of the Boolean statement.
4. A measured limit: a 169,856-word Shinigami executable does not fit the pinned privacy profiles because the bootloader must load and hash it.

Not established:

- Shinigami is not proved under the privacy bootloader, so no Shinigami statement reaches the Boolean relation yet. The S3q proof is a standalone-executable proof at the laboratory profile and is not an input to this verifier.
- Nothing is garbled at this size, no Bitcoin script exists, and the dispute protocol is untouched. The two public values (preprocessed root, output digest) must be bound by the on-chain commitment; that binding is not built.
- The output digest binds the bootloader's output preimage; that it commits to the Shinigami program hash and output words is not yet shown for the privacy bootloader.
- No claim is made about the soundness margin of the configurations beyond upstream's own constants.

## Reproduce

```bash
# WSL or Linux, nightly-2026-01-15
cd nova-bitvm3/stark-bitvm3/s4-cairo
cargo build --release
FIX=$(find ~/.cargo/git/checkouts -type d -path '*/e9a38e1*/test_data/multiverifier' | head -1)
target/release/stwo-bitvm3-s4-cairo check "$FIX"                 # native + Boolean + mutations
# production-config proof (WSL, 14.6 GB; separate crate, -C target-cpu=native)
#   cd ../s4-prove && cargo build --release
#   target/release/stwo-bitvm3-s4-prove PIE.zip OUT_DIR            # or EXECUTABLE.json OUT_DIR ARGS.json
#   target/release/stwo-bitvm3-s4-cairo check-prod OUT_DIR/recursion_raw.bin OUT_DIR/output_digest.hex
target/release/stwo-bitvm3-s4-cairo final --analytic              # production final verifier template
target/release/stwo-bitvm3-s4-cairo final-fixture --boolean --analytic
target/release/stwo-bitvm3-s4-cairo cairo --analytic              # Cairo verifier circuit (add --program-words N)
cargo test --release
```

CI runs the same through the opt-in `s4-verifier-circuit` job (`[s4-check]` in a push commit message, or the `s4_verifier_circuit` dispatch input). Results are in [S4_RESULTS.json](S4_RESULTS.json).
