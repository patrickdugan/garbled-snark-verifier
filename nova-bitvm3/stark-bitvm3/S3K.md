# S3k: source-pinned component-local Cairo relation diagnostic

## Motivation

The full-trace relation tracker exceeded **4 GiB sampled RSS** in both S3h and S3j before yielding any tuple. S3j already removed unused interaction-tree reconstruction; its evidence indicates that rebuilding the complete preprocessing and base trees remains too expensive for the current CPU runner. The original `canonical_small` Shinigami proof has a nonzero LogUp residue, and the native prover assertion must continue to reject it.

S3k narrows the diagnostic to the **`range_check_11` component**, a source-pinned 2,048-row range-check table whose claimed interaction sum was nonzero in the earlier 37-component S3f log. This stage records the component's own relation entries and field tuples. These entries are a *partial* relation inventory; contributions from other components and public memory are needed to determine full cancellation.

## Implementation

`s3-shinigami/tools/instrument_local_relations.py` verifies a clean checkout of `starkware-libs/stwo-cairo` at `467d5c6d4d6d526c1db8ff69c14f2de6d57f4d73`. It applies a temporary, source-pinned patch to the native prover and its diagnostic tracker. The original global LogUp zero-sum assertion is preserved.

The selected component exposes the exact preprocessed column indices and base trace spans through upstream's `FrameworkComponent` API. S3k reconstructs **only** those source polynomials into a sparse column table, preserving the original tree indices while leaving every unneeded column empty. Its target evaluation domain is the component's canonical `CanonicCoset::new(11).circle_domain()`, which enforces the original 2,048 rows even for constant-degree polynomials. Before passing the columns to the native evaluator, it checks their polynomial degree, row count, component log size and selected-column upper bounds.

The component relation entries are generated by upstream's **unmodified `add_to_relation_entries`**, preserving bit-reversed row and mask semantics. `RelationSummary::summarize_relations` handles duplicate tuple multiplicities modulo M31. This selected diagnostic never replaces the native proof relation or asserts globally balanced relations.

`tools/summarize_local_relations.py` requires the pinned global QM31 residual and a native failure with exit code 101. It validates the selected component, 2,048-row shape, entry count, strict output delimiters and raw relation names. Every report explicitly sets native proof verification, garbled verification and Ark/UTXORef/Bitcoin authorization to **false**. Python regression tests check source drift, partial-result semantics, and malformed logs.

## CI and evaluation

Routine CI tests source transformations and parser logic without starting Cairo proving. A separate `[s3-local]` commit or manual `s3_local_relation_audit=true` dispatch triggers **one** native diagnostic on the existing immutable standalone Shinigami CSV trace. The source-matched build retains 600-second compilation, two workers, and the 15-minute job cap; the native run retains **4 GiB sampled RSS** and **120 seconds**. The original native equality assertion must still fail for the experimental diagnostic to count as successful.

A passing diagnostic establishes only that one selected component's entries were reconstructed and independently reported under the CPU budget. More components and their counterpart contributions will be needed for a globally reconciled relation inventory. A native-verifiable Shinigami proof, matching Boolean verifier, application semantics, and Bitcoin-enforceable BitVM3 settlement remain separate acceptance gates.
