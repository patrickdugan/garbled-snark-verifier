# S5: the whole final verifier as one garbled circuit, evaluated on a Shinigami proof

S4 ended with a Boolean relation of 4,783,261,848 non-free ANDs that accepts Shinigami receipts when it is evaluated directly. S5 garbles that relation, all of it, with the repository's half-gates engine and evaluates the garbled circuit on the Shinigami proof: the evaluator ends with the garbler's **accept** label for the honest witness and with the **reject** label for a mutated proof.

Nothing here is a Bitcoin transaction. S5 is the off-chain object a BitVM3 dispute would be about, at full size, on a laptop.

## Result

A second run reproduces the same commitment, so garbling is deterministic for the seed. A second statement, the rejecting receipt `csv_below_delay`, gives the same ciphertext count, the commitment `9b3a114e87951fa68b3d6e483f77ca7377e371b5ac563671e5ad00f078df13cb`, the accept label for its honest witness and the reject label for its mutated proof (326 s, 11.5 GB). A receipt whose verdict is "rejected" is still a true statement about what Shinigami computed, so its proof is accepted.

The ciphertext count is 2.3% above the monolithic AND count (4,783,261,848) because a variable read by several pieces is decoded and range-checked in each of them; 1,177 of the gates are the combining AND chain.

## How pieces form one circuit

The Boolean program is cut exactly as for the direct check in S4 (`shard.rs`): slices of the constraint list, then groups of variables no constraint touches. Garbling 1,178 small circuits independently would not be one garbled circuit. Three rules make it one (`garble.rs`):

1. **One label pair per input bit.** The zero label of raw input bit `b` of global variable `v` is a keyed BLAKE3 of `(v, b)`; the one label is that XOR delta. A variable read by several pieces therefore carries the same label in all of them: one opened label per input bit serves every piece that reads it, and no piece can be fed a different value for a shared variable.
2. **One delta, one hasher key, disjoint gate numbers.** All pieces are garbled under the same seed, hence the same delta, constant labels and AES hasher key. Each piece numbers its gates in its own range (`index << 36`), so no gate tweak is used twice. Without this, two pieces that read the same input label at the same local gate number would produce related ciphertexts. The engine gained `GarbleMode::with_first_gate_index` and `EvaluateMode::with_first_gate_index` for this.
3. **One output.** A last piece ANDs the acceptance wires of all pieces. Its inputs are the output label pairs of the pieces, so it is garbled under the same delta and its single output wire is the circuit's verdict.

Per piece the run checks: ciphertext count equals the engine's non-free gate count and the direct AND count; the evaluator consumes exactly the piece's ciphertexts; the evaluated plaintext verdict equals the direct verdict; the evaluator's label equals the garbler's label for that verdict and differs from the other one. A piece's ciphertexts are hashed, used for the evaluations and dropped.

Unit tests (`cargo test --features garbled`): on the all-gate fixture, piece sizes 1, 3 and 1,000 give the direct verdict and the right output label for the honest witness and for a set of rejected ones; with a single piece the ciphertext count equals the monolithic AND count; the commitment is stable for a seed and changes with the seed.

## A defect found in the engine on the way

The first attempt used 2,000-constraint pieces, as the direct check does, and died inside the engine with "Called evaluate_gate for WireId(..) that was created but not initialized". Cause: the engine tracks the remaining reads of every wire in a 16-bit counter, and the metadata pass added to it with an unchecked `+=`. In release builds that wraps silently. Twenty of the 589 pieces (the first is number 114) contain input wires that are read 70,002 times each: the 124 value bits of one variable that all 2,000 constraints of the piece use. The wrapped counter freed such a wire early and a later gate read a recycled slot.

Three changes:

- `src/circuit/component_meta.rs`: the addition is now checked, so a fan-out beyond the counter is a hard error in every build profile instead of silent corruption.
- `garble.rs` measures the largest fan-out of each piece with a counting backend before garbling it and refuses a piece near the limit; `s4-cairo fanout N` prints the same measurement for the production final verifier.
- Garbling uses 1,000-constraint pieces: worst fan-out 35,002 over 1,178 pieces (2,000 gives 70,002; 500 gives 17,502).

## What this is not

- **No Bitcoin.** No script, no transaction, no dispute game. S5 produces and checks labels and a ciphertext commitment.
- **Laboratory label handling.** The seed is fixed, and the evaluator's input labels are selected directly from the garbler's pairs. There is no oblivious transfer and no on-chain commitment to input labels, so the binding of the evaluator to one witness is by construction of the experiment, not by a protocol.
- **Statement baked in.** The eight public output words are constants of the circuit, so one garbling serves one statement. A deployed design would more likely leave them as inputs whose labels are opened; the difference is 8 of 2,961,135 variables.
- **No proof that the garbling is correct.** There is no cut-and-choose and no verifiable garbling; the garbler is trusted here. The ciphertext stream is hashed, not stored, and not checked by a second party.
- **Laboratory profile.** The statement is the L21 one of S4e, with the same caveats (unreviewed parameter combination, pilot receipt without signatures).
- The engine's 16-bit read counter remains a size limit on any single piece; pieces must be cut so that no wire is read more than 65,534 times.

## Reproduce

```bash
# WSL or Linux, nightly-2026-01-15; about 6 minutes on 16 threads, 11.5 GB
cd nova-bitvm3/stark-bitvm3/s4-cairo
RUSTFLAGS='-C target-feature=+aes' cargo build --release --features garbled   # AES-NI is a compile-time choice
cargo test --release --features garbled
BIN=target/release/stwo-bitvm3-s4-cairo
$BIN fanout 1000
$BIN garble-lab fixtures/shinigami/csv_valid/recursion_raw.bin fixtures/shinigami/csv_valid/output_preimage.json
# S5_THREADS=N limits the worker threads (memory is about 0.7 GB per thread)
```

CI: the opt-in job `s5-garble` (`[s5-garble]` in a push commit message, or the `s5_garble` dispatch input) builds the feature, runs the unit tests and the full garbling of `csv_valid` on a hosted runner. [Run 42962782742](https://github.com/patrickdugan/garbled-snark-verifier/actions/runs/42962782742) (commit `dac161c`, 4 threads): the same 4,893,461,084 ciphertexts and the **same commitment** `517d4e1a...8621` as the laptop, accept label for the honest witness, reject label for the mutated proof, 745 s for garbling and both evaluations, 5.3 GB peak; the three unit tests pass. The `s4-verifier-circuit` job of the same run passes with unchanged counts after the sharding refactor. The repository's separate Code Checks workflow ran because `src/` changed: its formatting job passes, and its spelling and unused-dependency jobs fail as they already do on `main` (four old spelling hits under `nova-bitvm3/m14`). Results are in [S5_RESULTS.json](S5_RESULTS.json).
