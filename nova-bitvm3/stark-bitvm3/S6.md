# S6: the final verifier as a function of the proof

S4 and S5 lowered and garbled a *relation*: every variable of upstream's verifier circuit is a witness input, 379,025,280 bits of them, and each gate is a constraint between inputs. That is the right shape for checking a witness and the wrong one for a garbled circuit in a BitVM3-style protocol, where every input bit needs a label that somebody has to authenticate. Nobody can authenticate an execution trace.

S6 reads the same circuit as a *function*. Its inputs are the statement and the proof; everything else is computed inside. The result, for the production final 1-to-1 verifier:

| | Relation form (S4, S5) | Function form (S6) |
|---|---:|---:|
| Input bits | 379,025,280 | **2,375,891** (512 statement, 2,375,379 proof and advice) |
| Non-free ANDs | 4,783,261,848 | **1,720,551,518** |
| Ciphertext stream at 16 bytes | 76.5 GB (78.3 GB in pieces) | **27.5 GB** |
| Statement (root, digest) | constants of the circuit | **inputs**: one garbling serves every statement |

The raw recursion proof is 263,812 bytes, 2,110,496 bits, so the typed input is within 13% of the proof itself.

## How the circuit becomes a function

Upstream's circuit language has no notion of input. A context creates variables; some are *guessed* (values supplied from outside), the rest are outputs of gates. When a context is finalized, upstream adds one self-referential gate per guessed variable to fix its type (`Context::finalize_guessed_vars` at the pinned revision):

| Upstream guess | Gate added at finalization | Input type here | Bits |
|---|---|---|---:|
| 16-bit unsigned integer (halves of hash words) | `M31ToU32 { input: v, out: v }` | `U16` | 16 |
| Base-field element | `PointwiseMul { v, one, v }` | `M31` | 31 |
| Extension-field element | `Add { v, zero, v }` | `Qm31` | 124 |

`lowering::Function` (new, in the lowering crate) recognizes exactly these gates and turns them into typed inputs; they are not lowered, because they hold by construction once the input has that type. Every other gate is scheduled after everything it reads: a gate whose output has no value yet *defines* it, a gate whose output already has one *checks* it. A variable that is neither a pinned constant, a typed guess nor computed is refused (`Error::Undetermined`), so nothing is left for a prover to choose silently. The final verifier has 100,361 guesses (83,616 `U16`, 11,165 `M31`, 5,580 `Qm31`), equal to upstream's own guess counter, and 1,077,360 scheduled gates.

Three points deserve a sentence each:

- **Constants** are wires of the circuit, not checked inputs, so everything upstream derives from them folds away.
- **Permutation gates** do not say which permutation their outputs are; upstream fills the outputs in natively. Here they are computed: the inputs sorted ascending as 124-bit integers. That is always sound (a sorted copy is a permutation). It is complete when the rest of the circuit accepts only that order, which holds for this verifier: it permutes `value + key * u` with distinct keys and then requires the keys to ascend. All 9,310 computed permutation outputs equal upstream's on every proof checked below. A permutation gate whose outputs are guesses is still a multiset check.
- **The statement is input.** The final verifier guesses the output digest and the preprocessed root first, as 32 16-bit values, so the first 512 input bits are the statement; the checker verifies that they spell the digest and root of the receipt. The eight output words that S4 pinned are computed and no longer needed: they exist for chaining proofs, not for deciding acceptance.

The AND count falls by a factor of 2.78 because a computed value needs no range check, no equality check against a claimed result, and no packing check when it is produced by a gate that packs.

## Evidence

**Lowering crate** (default CI, Rust 1.90): on the all-gate fixture the function computes the witness the relation accepts; for each of the 915 single-bit changes of the input, the function's verdict equals the *relation's* verdict on the assignment the function computed (773 rejected, 142 accepted); non-canonical limbs are rejected; the gate order does not matter; untyped, doubly typed and self-defining variables are refused; permutation outputs come out in ascending order.

**Upstream differential** (default CI): a circuit finalized by upstream's own code is imported as a function. It computes upstream's witness, and for each of the 1,070 single-bit input changes its verdict equals upstream's native checker on the computed assignment (773 rejected, 297 accepted). This covers both the checks and the computed values, since the native checker also checks the defining gates.

**The real verifier on the Shinigami proof** (`s4-cairo check-func-lab`, fixture `csv_valid`):

| Check | Result |
|---|---|
| Honest proof | accepted; **2,860,426 computed variables compared with upstream's witness, 0 differ** |
| Six proof mutations (as in S4), each against upstream's re-synthesized witness | all rejected by the native relation and by the function; 0 computed variables differ from upstream in any of them |
| One digest bit, one root bit changed in the statement input | rejected |
| A non-canonical field input (limb equal to p) | rejected |

**Garbled** (`s4-cairo garble-func-lab`, feature `garbled`): the function is garbled once under one delta and evaluated on the honest proof and on a changed proof. As in S5 each piece has its own gate-number range and a last piece ANDs the check wires. New here: a variable computed in one piece enters later pieces with the label pair it left with, and the only labels from outside are those of the typed inputs.

| Quantity | Value |
|---|---|
| Pieces | 3,618 under one delta, over 498 depth layers |
| Ciphertexts | **1,720,551,518**, that is 27,528,824,288 bytes at 16 bytes each |
| Gates in all | 5,855,251,766 |
| Ciphertext commitment (default plan) | `237b36d4214f5a1b141950da915f1f998b27fcd4427e85ae2de691dbfdbba2f0` |
| Labels of wires handed between pieces checked against the garbler's pair | 71,056,672 |
| Handed-on values compared with upstream's witness | 1,273,280, 0 differ |
| Largest wire fan-out in a piece | 1,891 (the engine's limit is 65,534) |
| Honest proof | accepted, output label **is the accept label** |
| Changed proof (`trace_at_oods[0] + 1`) | rejected in 20 pieces, output label **is the reject label** |
| Time | 417 s on a hosted 4-thread runner; 1,056 to 1,216 s on this laptop under WSL with 16 threads |
| Peak RSS | 2.3 GB on the runner, 3.1 to 3.3 GB on the laptop; nothing is written to disk |

The second run of the default plan reproduced the commitment. A unit test on the fixture shows the property the table cannot: the ciphertexts do not depend on what is evaluated. One garbling gives the accept label for two different accepted inputs and the reject label for a rejected one, with the same commitment.

## Pieces and parallelism

Function pieces are not independent the way relation pieces were: a piece needs the wires earlier pieces computed. Cutting the evaluation order into consecutive chunks made the dependency graph a chain (longest chain 748 of 759 pieces) and the first full run took 52 minutes on one thread. The plan now cuts by dependency depth (`func.rs`): gates go into layers by the length of the longest gate chain below them, gates of a layer that feed each other form a component, and components of one layer cannot depend on each other. The verifier is 2,988 gates deep. With 512 layers and pieces of about a million ANDs the heaviest dependency chain carries a ninth of the estimated work, and the run takes 7 minutes on a hosted runner. The commitment depends on the plan, because pieces number their gates; the ciphertext count does not.

Where it runs matters more than the thread count. A hosted 4-thread runner finishes in 417 s. This laptop under WSL needs 1,056 to 1,216 s with 16 threads and 2,285 s with 4, and spends about 9,400 processor-seconds either way, three times what the single chain of 759 pieces cost on one thread here. So the layered plan carries a per-piece cost in this environment that the runner does not show. It was not investigated; the allocator was changed to mimalloc on the way, which helped the direct executor.

## What this changes for BitVM3, and what it does not

With the function form the object a dispute would be about is concrete: a 27.5 GB garbled circuit with 2,375,891 input wires, of which 512 are the public statement.

It does not make the input cheap to authenticate. Opening one 16-byte label per input bit on Bitcoin is 38 MB of labels before any script that checks them, against a 4 MB block; a per-bit hash lock for both labels adds several times as much. The proof labels cannot go on chain, not even in a dispute path that is meant to be affordable. That leaves these routes, none of them built:

1. **Only the statement on chain.** The 512 statement labels are opened on chain (about 8 KB); the garbler hands the proof labels to the evaluator off chain. Soundness holds, since whatever labels the evaluator receives, the circuit verifies the proof they encode against the opened statement. What is missing is a guarantee that the labels are handed over at all, which is a data-availability assumption or a forced-publication game with its own cost.
2. **A succinct proof in front.** Wrap the recursion proof in a proof of a few hundred bytes and garble that verifier instead. This is the route of the Nova and SP1 workstream in this repository; it buys a small authenticated input with a trusted setup or pairing assumptions.
3. **A smaller STARK proof.** Fewer queries at a higher blowup shrink the input but stay in megabits.

Also not done: there is still no Bitcoin script and no dispute game; the garbler is trusted to garble correctly; the seed is fixed and the evaluator's input labels are selected directly; the statement is the laboratory profile L21 of S4e with the S3 pilot receipt.

## Reproduce

```bash
cd nova-bitvm3/stark-bitvm3
cargo +1.90.0 test --locked --manifest-path lowering/Cargo.toml --features test-utils      # function form vs relation form
cargo +1.94.0 test --manifest-path upstream/Cargo.toml --test conformance                  # vs upstream's native checker

cd s4-cairo                                                        # nightly-2026-01-15
cargo build --release && cargo test --release
BIN=target/release/stwo-bitvm3-s4-cairo
$BIN final-func prod                                               # inputs, gates, plan
$BIN check-func-lab fixtures/shinigami/csv_valid/recursion_raw.bin fixtures/shinigami/csv_valid/output_preimage.json

RUSTFLAGS='-C target-feature=+aes' cargo build --release --features garbled
$BIN garble-func-lab fixtures/shinigami/csv_valid/recursion_raw.bin fixtures/shinigami/csv_valid/output_preimage.json
# S5_THREADS=N limits worker threads; S6_LAYERS and S6_PIECE_ANDS change the plan (and the commitment)
```

CI: the function-form tests of the lowering and upstream crates run in the default jobs. The opt-in jobs `s4-verifier-circuit` (`[s4-check]`) and `s5-garble` (`[s5-garble]`) run `final-func`, `check-func-lab --light` and `garble-func-lab` on a hosted runner. [Run 42994147792](https://github.com/patrickdugan/garbled-snark-verifier/actions/runs/42994147792) (commit `d698073`, all five jobs green): the same sizes; the function computes 2,860,426 variables with no difference from upstream and rejects the changed proof, both statement bits and the non-canonical input (37 s); the garbling gives the same 1,720,551,518 ciphertexts and the **same commitment** `237b36d4...a2f0`, the accept label and the reject label, in 417 s with 2.3 GB; the relation-form garbling of S5 reproduces its commitment as well. Results are in [S6_RESULTS.json](S6_RESULTS.json).
